> 最后更新：2026-11-05
> 当前阶段：B0/B1/B2/B3 全部完成并通过回归（后端全量测试、前端构建、桌面端弹窗与横幅自查）
> 代码入口：`backend/app/media_studio/services/episode_video_service.py`、`backend/app/media_studio/services/timeline_rendering.py`、`backend/app/minimax_h3_refine_workflow.py`、`frontend/src/director2/panes/EpisodeWorkshopPane.tsx`、`frontend/src/director2/director2-video-settings.ts`、`frontend/src/director2/assistant/episode-shot-tasks.ts`
> 用途：解决「整集直出模式下，已生成的镜头被无谓重跑」的问题，分三个增量交付：B1 提交检测与确认、B2 连续区间补跑（尾帧锚定）、B3 续写式整集直出。每完成一个增量更新第 2 节状态表，并按 `AGENTS.md` 同步 ARCHITECTURE / 扩展指南 / 流程快照。

## 1. 目标与边界

### 1.1 问题背景

- 逐镜模式下「生成全片段视频」已自动跳过已有成片镜头（`generate_episode_videos` 的 `skip_existing`）。
- 整集直出模式（`render_scope=episode`）不检测已有成片，永远整集重跑：单独跑过镜头 1 后再点「生成全片段视频」，镜头 1 会被重新生成。
- 但整集直出的价值恰恰在于**组内连续生成**（运镜、光线、角色、音频在同一条 timeline 上生长），不能简单「跳过前 k 镜」：
  - 渲染的最小单位是组（chunk），`plan_timeline_chunks` 把**连续**镜头按段数/帧数上限打包，跳过组内单个镜头不可行；
  - 若用户单独跑过 1、3、5，把 2、4 当邻居编进同一条时间线，生成上下文邻居与叙事邻居错位，污染组内连续性。
- 正确规则：**按最大连续缺失区间补跑**，且每个区间用前一个已有成片的**尾帧**做锚定，把接缝压到区间边界。

### 1.2 三个增量

| 增量 | 内容 | 依赖 |
| --- | --- | --- |
| B1 | 整集直出提交前检测已有成片镜头，确认弹窗如实告知代价，并提供「只补跑未生成镜头」入口（B2 未上线前先落到勾选式 selection 提交） | 无 |
| B2 | 尾帧锚定原语 + `strategy=gap_fill`：后端求最大连续缺失区间，每区间建一个 selection Timeline 任务，区间首镜以前置成片尾帧锚定 | B0 spike |
| B3 | 续写式整集直出 `strategy=continue`：已出片镜头构成**连续前缀**时，整集计划剔除前缀、第一组锚定前缀尾帧，剩余集内容连续生成；前缀不连续时自动回退 B2 | B2 |

### 1.3 硬约束

- 不改变逐镜模式既有跳过行为；不改变 `selection`/`compose`/一采二采/超清/重试缓存（`previous_chunks` 组级复用）语义。
- 不新增数据库表；补跑任务全部复用 `ai_project_jobs`（`render_scope=selection/episode`），锚定信息写入 payload。
- 不新增第二套 ComfyUI；锚定帧上传只走 `ComfyVideoClient.upload_image` 既有通道；远端实例以管理设置生效地址为准。
- 前端不硬编码工作流能力；模式判定继续走 `episodeVideoRenderMode` / 后端 `episode_video_render_mode`。
- 锚定效果必须如实表述：若 spike 结论是「只能作参考图而非严格首帧」，UI 文案写「强一致性锚定」，不得承诺无缝衔接（证据真实原则，同智能剪辑助手）。
- 双主题、Ant Design 组件库、`--studio-*` token 规范照常适用。

### 1.4 当前明确不做

- 不做移动端适配。
- 不做「任意乱序镜头逐个锚定续写」（如 2、4 分别单独锚定拼接）——只支持连续区间。
- 不动 Recipe 旧九阶段管线；本计划只作用于导演台分集工坊（director2）。
- 不为补跑引入新的工作流节点 ID；需要变化时按规则复制为新工作流。

## 3. 现状机制速览（开发前必读）

以下为 2026-11-05 核实的代码事实，实现时以最新代码为准：

1. **入口分流**：`EpisodeVideoService.generate_episode_videos`（L328）——`beat_ids` 为空且整集模式 → 1 个 `episode` 任务（`skipped` 恒 0）；逐镜模式 → 逐镜建 `shot` 任务，已有 `video_url` 或生成中的跳过。勾选镜头时 `beat_ids` 非空 → `render_scope=selection`，`force=True`（不跳过）。
2. **分组**：`plan_timeline_chunks`（`timeline_rendering.py` L111）按 `max_segments` / `max_total_frames` 把连续镜头打包成组；组是渲染与缓存的最小单位。
3. **组级重试缓存**：episode 执行器（`episode_video_service.py` L2200 附近）用 `previous_chunks`（按 shot_ids 元组匹配 payload 旧 `render_plan.chunks`）复用**同一任务重试**时已成功的组；不跨任务、不看 beat.video_url。
4. **按镜落地**：`_split_and_publish_shots` / `_write_selected_beat_videos` 已把 timeline 输出按镜切分回写 beat，并记录 `shot_clip_urls`（beat_id → 本镜独立成片 URL）——**尾帧锚定的素材来源优先用 `shot_clip_urls`，回退 `beat.video_url`**。
5. **参考图上传**：执行器对每个 shot 的 `reference_urls` 调 `comfy.upload_image`（L2093-L2107，带 sha1 缓存），锚定帧沿这条通道进入 `uploaded_refs`。
6. **续跑工作流雏形**：`continuation_workflow`（`minimax_h3_refine_workflow.py` L419）目前服务一采/二采，证明「在已生成 workflow 上改输入再跑」的模式可行，可借鉴但不直接复用。
7. **前端拦截**：菜单项在 `episodeVideoJobActive` 时置灰；`activeEpisodeVideoJobs` 对 `episode/compose` 返回 blockingJobId、对 `shot/selection` 返回 activeBeatIds——**注意当前同集存在运行中的 selection 时，再次整批提交仍会被逐镜口径放行**，B2 多区间并发排队需按第 5.3 节处理。

## 4. B0 — 锚定能力 Spike（先行，1 天内）

目的：确定 B2/B3 的锚定注入方式，产出结论写回本文档第 4.3 节。

1. 用远端 ComfyUI（管理设置生效地址）现有整集 timeline graph 做只读探测：首镜节点是否存在严格「首帧图像」输入槽；若无，确认参考图（R2V 有序 `<Picture n>`）语义下追加锚定帧的可行位置与上限（9 张参考图约束）。
2. 验证尾帧抽取链路：下载 `shot_clip_urls[beat_id]` → FFmpeg 抽最后一帧 PNG（复用智能剪辑助手 A3/A4 的帧抽取工具路径，位置在 `backend/app/director_assistant/`，spike 时确认具体函数）→ `comfy.upload_image` 上传成功可被 workflow 引用。
3. 小规模冒烟：2 镜小组 timeline 任务，首镜带锚定帧跑通并肉眼比对衔接。

### 4.3 Spike 结论（2026-11-05 完成）

- **锚定方式：严格首帧（已实测验证）**。`MiniMaxH3Director` 节点支持在全局 `r2v` prompt_batch 时间线内对**单个段**覆盖 `taskType: "fl2v — 首尾帧生视频(First-Last Frame)"`：`gen_timeline.py _resolve_segment_task` 允许任意非空段级 taskType（不要求全局 mixed），段级 `startImage.imageFile` 经 `_load_fl2v_segment_refs` 重建为 SegmentRef(0)=首帧锁，走官方 `MiniMaxH3ImageToVideo.execute(first_frame=…)`。远端 192.168.10.54:8188 冒烟：2 段时间线（段 0=fl2v 锚定、段 1=r2v）跑通 112 帧，输出第 0 帧与锚定帧平均像素差 0.0217（压缩噪声级），锁定成立。
- **注入槽位**：锚定图上传后把返回的 `imageFile`（`"<subfolder>/<name>"`，节点按 ComfyUI input 目录相对路径解析，见 `plan.load_reference_tensor`）写入锚定段 `startImage.imageFile`；`genImage.imageFile` 为兜底位（`_fl2v_image_raw` 顺序 startImage → genImage）。工作台自己的 `build_timeline` 段结构里 `startImage` 字段直接新增即可。
- **尾帧抽取与上传**：本地 FFmpeg 抽最后一帧 PNG（`-sseof -0.1 -i … -frames:v 1`，或按帧号 `select=eq(n,N)`）→ 复用 `ComfyVideoClient.upload_image`（既有 sha1 缓存通道、`zly-ai-media/…` 子目录约定）→ 返回 dict 的 `imageFile` 直接作锚定段 `startImage.imageFile`。
- **已知限制**：
  1. fl2v 段**只消费首/尾帧两个图槽**：实测（2026-11-05 ep-5d0e14baaf55 第 3 集）段内残留的 `refs[0]` 会被节点当成**尾帧**，导致补跑镜头的成片最后一帧直接变成角色参考图三视图；并非早前记录的「节点自动剥离参考图」。修复：`build_timeline` 锚定段必须显式 `refs=[]`（提示词 `<Picture n>` 已由 `_prepare_anchor_frame` 剥离），外观一致性由锚定帧自身承载；回归断言见 `backend/tests/test_episode_gap_fill.py::test_timeline_anchor_segment_becomes_fl2v_with_start_image`。
  2. 锚定是静态帧级锁定：跨任务无 latent/音频连续性，区间边界的音频仍是独立生成。
  3. 锚定帧画布由节点 `_fit_image`/`_unify_fl2v_pair_canvas` 统一到输出画布，长宽比不一致时会被裁切/适配。
- 冒烟脚本与产物：`.tmp/b0-spike/`（`smoke_anchor.py`、`verify_chain.py`；临时排查产物，不提交）。

## 5. 方案详细设计

### 5.1 B1 — 提交检测与确认（纯前端 + 文案）

**文件**：`frontend/src/director2/director2-video-settings.ts`（新增纯函数）、`panes/EpisodeWorkshopPane.tsx`（`handleGenerateEpisodeVideo` 前插确认）、新增测试。

1. 新增纯函数 `computeEpisodeGapSegments(beats)`：输入按 sequence 排序的 beats，输出最大连续「无 video_url」区间列表 `Array<{ startSeq, endSeq, beatIds }>`（该函数是 B2 后端区间算法的前端镜像，边界规则写进测试：全空 → 一个全片区间；全有 → 空列表；首镜已有、后续缺 → 从第一个缺失开始）。
2. `videoRenderMode === "episode"` 且存在已有成片镜头时，提交前 `Modal.confirm` 三选一：
   - **整集重渲（保证全片连续）**：维持现状，文案写明「含已有 M 镜将全部重新生成」；
   - **只补跑未生成镜头（推荐）**：B2 未上线前 = 自动勾选缺失区间镜头并走既有 `beat_ids` selection 提交（`formatSelectedShotSubmitMessage` 回显），文案如实提示「区间起点与已有镜头存在衔接跳变」；B2 上线后 = 提交 `strategy=gap_fill`；
   - **取消**。
3. 已有成片为 0 或逐镜模式时不弹窗，行为与现在完全一致。
4. 弹窗文案随主题 token，不新增颜色硬编码。

### 5.2 B2 — 连续区间补跑 `strategy=gap_fill`（后端为主）

**API**：`POST /api/projects/{project_id}/episodes/{episode_id}/generate-video`，payload 增加可选 `strategy: "gap_fill"`（仅整集模式接受；逐镜模式收到该字段忽略并维持现有 skip_existing 行为，保证旧前端兼容）。

**后端**（`episode_video_service.py`）：

1. 新增 `_compute_gap_segments(shots/beats)`：与 5.1 相同规则的区间划分（后端为唯一权威，前端函数只做预期展示），跳过已有 `video_url` 与 active 任务覆盖的 beat。
2. 每个区间调用既有 `create_job(beat_ids=区间, render_scope="selection", options=…)`，payload 附加：
   - `gap_fill: true`、`segment_index / segment_total`；
   - `anchor_beat_id`（前置已出片镜头 id，区间无前缀时为空）、`anchor_source_url`（优先 `shot_clip_urls`，回退 `beat.video_url`）。
3. 执行器扩展：selection/timeline 任务发现 `anchor_source_url` 时，在参考图上传阶段（L2093 附近）抽取锚定帧（FFmpeg 抽尾帧 → 临时 PNG → `upload_image`），按 B0 结论注入区间首镜（严格首帧槽或追加为有序参考图末位并同步提示词 `<Picture n>` 计数）。
4. 响应：`{ render_mode: "episode", strategy: "gap_fill", job_ids: [...], submitted: N, skipped: M }`；`formatEpisodeVideoSubmitMessage` 增加 gap_fill 分支「已补跑 N 个镜头（跳过 M 镜已有成片）」。
5. 全部镜头已有成片 → `ValueError("全部镜头已有成片，无需补跑")` → 400，前端 message 展示。

**5.3 并发与排队（B2 一并处理）**：

- `_assert_can_enqueue` 现口径：episode/compose 运行中会阻断分段任务；反向（分段运行中阻断整集）已有。**同集多个 gap_fill selection 任务允许同时处于 queued**，执行侧依赖 `occupy_gpu` 天然串行，不做区间合并大任务（保持每区间独立失败/重试）。
- 前端进度：`activeEpisodeVideoJobs` 已按 beat 收集 activeBeatIds，多 selection 并存时镜头卡逐镜回显无需改动；顶部横幅沿用 `workshopEpisodeStageLabel`，gap_fill 任务显示「补跑区间 i / n」。

**失败语义**：单区间失败不影响其他区间；失败区间可单独重新提交（重进「生成全片段视频」时该区间仍属缺失，天然可重试）。

### 5.3 B3 — 续写式整集直出 `strategy=continue`

**API**：同端点，payload `strategy: "continue"`（B1 弹窗在「已有成片构成连续前缀」时把推荐项从 gap_fill 文案升级为「从第 k+1 镜续写整集」）。

**后端**：

1. 检测已有成片是否构成**连续前缀** `[1..k]`（sequence 1..k 全部有 video_url 且 k ≥ 1）；不构成前缀（如 1、3、5）→ 自动回退 `gap_fill`，响应里 `strategy` 字段回显实际执行策略。
2. 构成前缀时：`create_job(render_scope="episode", beat_ids=[k+1..N])`（selection 分支已支持任意 beat 子集的 timeline 分组，episode 任务复用同一条 `_prepare_shots` 过滤链），payload 记录 `anchor_beat_id=k`、`anchor_source_url`。
3. 执行器：整集任务第一组首镜注入锚定帧（与 B2 共用同一锚定原语函数，禁止两处复制粘贴实现）；`output_start` 偏移沿用现有 assembly 逻辑，拼接成片时前缀部分直接取已有成片文件参与 `ffmpeg_concat`（`_merge_chunk_videos` / assembly 需支持「外部已有片段」参与合并，这是 B3 唯一的合成侧改动）。
4. 进度回显：整集任务 shot_status 从 k+1 开始编号，前端 `stampShotBeats` 按 beat_id 匹配，天然兼容。
