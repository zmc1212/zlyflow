## 1. 本轮方向与完成定义

2026-09-27 真实证据修订：原 Skill 的固定参考音频、固定图序和物件禁令与实际材料冲突。保留原 Skill 文件与 v1 冻结证据，新增导演台通用 Skill v2 作为新任务唯一默认版本，全文发送而非程序追加创作模板；历史重试不换版本。下文 P1 的“原始 Skill 完整一致”在 v1 验收中保留，在 v2 中核对该版本完整 Skill 文件与实发 system 的哈希一致。对白比较对 v2 仅忽略成对引用引号，不放宽字词、顺序或停顿，不改写输出。此修订用于解决正式入口的通用冲突，不授权额外付费样本，不把人工修订后的单个成片计为首次生成通过。

本次不是继续建设更复杂的审稿系统，也不是把满意成品当作模板让模型照抄。核心工作是收敛写稿输入和程序干预，使工作台承担材料整理、保存和执行职责，让 Skill 和作者承担创作职责。

用户确认的目标方式：

> 把指定 Skill 交给 Codex，读取扩写后的剧本，由其推理生成提示词；当时没有现在这套自动校验返修循环。

分开验收以下两项，不能相互替代：

1. **方式对齐**：Skill 完整、扩写内容完整、参考事实一致，没有额外模板和旧稿牵引，没有自动内容返修；创作正文没有被存储或提交链改写。
2. **效果达标**：对白完整清晰，动作与对白配合自然，人物、场景和镜间衔接达到用户认可的满意版水平。测试通过、提示词结构正确、任务成功均不代表效果达标。

本文替代 [2026-09-26 恢复计划](导演台满意版效果恢复开发计划-2026-09-26.md) 中与「继续加写作规则、依靠自动返修恢复质量」有关的后续方向。旧计划的取证、保真、并发和历史记录继续有效；不删除旧文档，不把旧计划的完成勾选移植为本计划已完成。

### 不在本轮范围内

- 不重做内容库、镜头规划、分组、资产管理或整个导演台界面。
- 不删除用户已经扩写的剧本，不为精简输入而退回梗概。
- 不修改原始 H3 Skill，不混入第二套创作 Skill。
- 不默认换模型、加推理强度、切换 ComfyUI、改采样参数或后期配音来掩盖写稿差异。
- 不承诺相同文字必然生成相同视频；模型能力与采样随机性另行记录。
- 本轮授权仅为制定计划；本文中的付费写稿、出片与采纳均为未来步骤，不在本轮执行。

## 3. 目标链路与职责

```text
已确认的扩写剧本／镜头创作内容 + 选中范围与时长 + 实际素材事实
                              ↓
                  唯一的最小写稿输入构造器
                              ↓
               完整原始 H3 Skill + 一次作者调用
                              ↓
        完整原稿保存 → 确定性拆分 → 候选预览与用户采纳
                              ↓
             素材／数据完整性／执行协议检查
                              ↓
                 原文编译 → 当前远端 ComfyUI
```

保留上游剧本扩写与分组能力；两镜、三镜可以共用主体定义。程序不再预写一套场景、声音或表演要求来牵引首次写稿，也不把 Director 的内部状态约束当作创作正文要求。

### 3.1 输入先对齐来源，再精简包装

P0 必须核实当时 Codex 读到的「扩写后剧本」具体来自哪里：内容库已采纳正文、镜头正文，还是旧 Director 扩写结果。`WorkshopService.source()` 当前读到的分集正文不自动等于当时的扩写材料。

确立并展示一个明确的创作来源版本：

- 完整分集剧本作为故事上下文，所选镜头的已确认扩写文本作为本次直接创作材料。
- 如果扩写内容分散在 `action`、`camera`、`audio` 等字段中，以白名单投影成一份可读材料；保持有效描述原文，不调用另一个模型摘要。
- `dramatic_intent`、表演、运镜、声景等若确为用户采纳的扩写成果，应归入这份材料，不能因字段名像元数据就删除。
- 同一段内容只出现一次。缓存的 `video_prompt_zh`、草图提示词等不能作为另一套同等权威的创作来源重复注入。
- 来源缺失、版本冲突、无法区分「用户扩写」与「程序生成缓存」时，不静默选择；显示具体来源冲突，让用户选择或确认版本。

### 3.2 最小输入合同

新增版本标识暂定 `h3-skill-direct-v1`；这是本计划的目标标识，当前尚未实现。只设一个新写稿入口，不给普通用户增加多套提示词引擎选择。

| 材料 | 处理方式 |
| --- | --- |
| 原始 Skill | 完整放入 system，不追加 v7 写作守则；保留原文件与实际发送文本哈希，明确换行／首尾空白处理 |
| 创作请求 | user 用简短自然语言说明根据材料生成本组完整 H3 提示词；不追加长篇表演规则 |
| 剧本与扩写材料 | 完整、可读、明确来源；不静默截断，超预算直接告知 |
| 范围与时长 | 指明选中的镜头、顺序、确认时长、画幅；内部 ID 与数据版本留在元数据中 |
| 参考图 | 按实际顺序给出 Picture 编号、人物／道具身份和用途；只声明已提供的素材，没有场景图／参考音频就如实说明 |
| 用户明确锁定项 | 原样传入并注明是用户要求；不能把程序自动生成的旧公共设定冒充锁定项 |
| 输出边界 | 完整公共主体／声音设定和所选镜头正文，沿用 Skill 的原生结构；仅保留解析与执行必需的短格式说明 |
| 时间基准 | 作为执行协议事实简短声明，具体采用累计还是段内秒数由 P0 实际节点证据确定；不加入字速、动作占比或静默时长模板 |

首次生成不注入：旧 `common_prompt`、旧 H3 成稿、字速估算、固定静默尾部要求、状态机术语、六段式模板、整份 Beat JSON、资产内部状态、自动审稿意见。

不预分配 Subject 编号或默认音色，作者根据 Skill 和真实材料统一定义；Picture 编号必须匹配实际图片顺序。写稿参考与最终视频参考继续隔离，不自动把人物设定板当首帧、把场景图改成 R2V 主体。

满意成品只用于离线验收，默认不进入首次写稿输入。单镜人工返修是明确例外：可加入当前完整稿和用户的定点意见，以保持邻镜与公共设定不变；不能因此让首次生成也读旧稿。

### 3.3 调用、失败与检查边界

- 首次生成默认一次内容生成调用，不执行「格式不满意 → 再喂原稿 → 自动重写」循环；关闭 `range(3)` 驱动的语义返修路径。
- HTTP 传输重试与内容重写分开记录。超时／连接失败不得暗中换作者、删图、切纯文本；不把多次生成记作一次成功。
- 无法解析的原稿仍保存并可查看，标明问题，用户可手动编辑、明确重试或定点返修；不能把不可解析稿标为可出片。
- 保留必要硬检查：访问权限、源版本、所选镜头映射、原对白完整性、实际图片编号、时长／帧数／节点参数合法性、正文完整与采纳指纹一致。
- 不以固定字速、覆盖每个 0.1 秒、必须出现「静默」或特定姓名写法决定创作质量。合法的 `<Subject N> (S1)` 与姓名归属按共享定义解析，不为了程序格式让作者重写表演。
- 保留现有内容风险分析作为不改稿的旁路提示，不自动反馈给模型，也不升级为成片质量认证。若用户要求返修，才把选定问题作为本次显式请求。
- 不新增语义审稿模型、自动配音或自动修复视频。内容选择与真实音画验收仍需人判断。

### 输入与原稿留痕

复用任务 JSON，新增版本化输入包与原稿信息，不新增数据库表：

- 来源类型、文档／扩写修订号、原文快照和哈希。
- Skill 原文、发送文本、输入包版本、system/user 实际文本及哈希。
- 所选镜头及顺序、确认时长、图像用途和有序参考清单。
- 请求模型、响应模型、实际发送的推理／采样设置、参考图是否实际发送、调用次数；未知明确为未知。
- 原始完整输出、解析结果、容器或时间表示转换记录、编辑／返修来源。

元数据用于复现与并发保护，不自动再作为创作输入。不要记录密钥、Authorization、带鉴权查询参数的链接或整份 Base64 图像；采用现有安全素材标识与内容哈希。

## 5. 实施顺序与阶段出口

### P0：冻结真实基准和最小实验条件

1. 复核原 Skill、满意稿、历史输入与原提交记录，补齐可找到的源剧本／扩写快照、图片身份和 graph；未知项单列。
2. 保存本次问题稿原始输入、初稿与最后返修稿作为反例，不只保存最终视频提示词。
3. 核实远端 `MiniMaxH3Director` 的时间码／独立 segment 语义。原稿使用累计文本、现有代码也可配置累计，不能只凭过去回答判为对或错。
4. 如确有时间基准错误，把「历史原文复现」与「显式协议修正版」分开编号；任何秒数转换都保留原稿、单独验证，不暗改后继续声称原样复现。
5. 建立隔离的两镜试验快照，采用满意稿的一张人物参考、8＋8 秒；不把生产三镜组拆掉，也不放开 `execution_plan()` 对任意半组出片的限制。试验复用正式编译链，不另写一套提交实现。

**出口**：源材料、选择范围、素材、时间基准及可复现执行条件有清单。历史材料不全时明确降格为「受控新对照」，不阻塞不依赖历史参数的代码工作，但不宣称历史原样复现。

### P1：先实现唯一最小输入构造器

1. 输入字段白名单与来源优先级落地，保留扩写的有效动作、镜头和声景。
2. 新合同中 system 与完整 Skill 对齐；user 只含第 3.2 节材料。所有调用入口引用同一构造器。
3. 可复制／导出完整输入包，供人工审阅及必要的 Codex 手工对照；导出与 API 实际发送文本来自同一快照，不维护第二套写稿规则。
4. 用反污染测试确认：改变旧公共稿、缓存视频提示词或任务状态，不影响首次写稿输入；改变已采纳扩写正文、素材或显式锁定项，必须改变输入哈希。

**出口**：不用调用任何模型就能逐段审查实际输入，确认它是所需创作材料，而不是程序规则集合。

### P2：移除新合同自动内容返修与写稿后的干预

1. 新任务按一次调用产出完整原稿，解析成功成为候选，解析失败保留原稿等待处理。
2. 检查生成、手动保存、采纳、重试、单镜返修和出片全链，不能残留旧格式门槛重新触发重写。
3. 单镜返修仍是用户明确操作；冻结邻镜和公共设定，超范围变动不静默采纳。
4. 确认默认声音注入、旧六段式转换和备用写稿入口不会回写新合同的输出。

**出口**：正常生成一次内容调用；无自动换作者／改图；实际输出正文在采纳和提交时保持原文。

### P3：兼容、界面与离线回归

1. 不改 v7 制作方案总结构；新合同使用任务／稿件附加版本字段。
2. 旧任务继续按原合同快照解释；旧稿、手工稿、媒体可查看，不批量改写。未记录版本的历史稿使用明确的旧兼容分支。
3. 重跑旧任务保留其合同；「按新方式重新生成」创建新任务并引用原任务，不原地替换合同。运行中的任务不切版本。
4. 界面提供原稿和输入来源，显示「可解析／候选待采纳／成片待验收」，不把规则通过写成质量通过；内容提示不是新的必经审稿工作流。
5. 在真实 5173 页面验证桌面浅／暗主题：生成、失败原稿、编辑、单镜返修、整组采纳、历史读取与未保存保护。

**出口**：离线测试、前端构建和桌面检查通过；只能标记「方式与代码验收通过」，不能提前勾选效果达标。

### P4：同条件真实写稿与两镜成片验收

先取得真实生成阶段的批次／费用授权，再执行；不因计划存在就自动调用付费服务。

1. **输入方式对照**：固定同一扩写源、两镜范围、一张人物参考和同一可用作者设置；保存旧输入构造与新输入构造各一次的完整输出，比较表演、对白归属和指令矛盾。禁用自动内容返修，避免把返修差异混入输入对照。
2. 作者沿用用户确认的现有供应商；本阶段不以必须找到某个 GPT 型号作为代码开发前提。无法同模型对照时标记额外变量，不能宣称只由代码造成差异。
3. **出片对照**：A 为满意稿原文，B 为新方式生成稿；使用同一远端实例、工作流、权重、参考图片及顺序、尺寸、fps、帧数、音频模式、连续性设置和 seed。必要的协议转换对 A/B 等价执行并记录。
4. 第一批只做一对 A/B。保留全部结果，不自动采纳，不只展示最好的一条；失败先判定文本、编译、执行还是媒体层，不盲目反复重生成。
5. 第一对通过后，建议用另外两个预先固定 seed 再做两对，检查明显随机性；这是最多三对的建议验收批次，不是本轮自动授权。预算不足时标记「单次通过，稳定性未验收」。
6. 记录视频 ID、文件／媒体标识、实际参数、听辨时间点和判定；有可靠转写可作辅助，但不以转写结果替代人听。

**出口**：双方样本完成音画比较，用户确认新方式达到了目标效果；否则保持未完成并归因，不自动扩展新审稿规则。

### P5：扩展到真实三镜组，再推广

两镜基准通过后，再验证生产场景的三镜、四张参考配置；这一步测试额外镜头和道具参考带来的变化，不与 P4 合并归因。

覆盖下一组有多人对白或场景变化的镜头，确认不是只针对「再查查出处」硬编码。组 1 效果未达标之前不批量重生成整集。用户明确采纳后才更新正式提示词／媒体引用。

**出口**：实际工作台可重复使用，当前问题句与其他镜头都通过；完成文档同步与回滚检查后关闭计划。

## 6. 验收用例与完成标准

### 6.1 代码与输入验收

- 指定 Skill 全文完整、哈希可核对；扩写正文中的关键段落和对白不被截断、摘要或重复。
- 导出输入与实际发送文本相同；transport 将图像内嵌不改变文本、图像顺序和用途。
- 初次输入不含旧 `common_prompt`、旧成稿、整份 Beat JSON、固定字速／静默规则或内部状态机字段。
- 有效扩写细节保留；无关缓存和状态变化不影响输入；源文本、用户锁定项和素材变化触发新指纹。
- 正常一次内容调用；可解析稿不自动二次润色；不可解析稿可回看，不能直接出片，也不会覆盖已采用稿。
- 满意稿及多样新稿覆盖原稿 → 拆分 → 保存 → 采纳 → timeline → 最终 graph；容器转换之外正文保持一致。
- 两镜／三镜、无对白／多人对白、单镜返修、累计／段内时间表示的执行合同各有测试。
- 同时覆盖版本过期、素材换图、并发采纳、取消、手动编辑、旧合同重试和回滚后的只读兼容。

新增正式用例可放 `backend/tests/test_workshop_direct_input.py`；扩展现有 `test_workshop_authoring.py`、`test_workshop_group_prompts.py`、`test_workshop_h3_skill.py`、`test_workshop_review.py`、`test_workshop_video_preflight.py`、`test_workshop_v7.py`。前端用例仍放 `frontend/src/**/*.test.ts(x)`。

### 6.2 音画验收

硬性失败项：

- 两句原文对白遗漏、重复、改词；特别是「再查查出处，应该还有线索。」句尾不完整或出现不可辨识伪语音。
- 多出人声、旁白或第三镜无对白却出现讲话；同一人物声音无故明显改变。
- 明显口型错位、背景声遮盖对白、音轨剪断。
- 原剧情动作遗漏或被禁项阻止；人物、道具身份明显漂移；镜间出现无法解释的状态跳变。

质量比较项：动作先后清楚、人物在做事而非机械念台词、语气符合查证情境、场景与灯光统一、镜头衔接自然。由用户对照满意稿效果确认，不拿文本长度、警告数量或任务成功率代替。

每条样本记录「通过／不通过／尚未听辨」与具体证据。任一关键对白失败不得记为该样本通过；多次重复的样本失败率如实保留。满意稿自身也在当前环境失败时，优先排查执行条件／音频模型等变量，不继续无限增加写稿规则。

## 8. 发布、文档与回滚

### 发布顺序

先实现版本化输入构造与一次调用，再统一检查和兼容，之后做最小界面增量；离线与桌面验收通过后进行有授权的真实对照。保留单一正式新写稿路径，旧版本仅承担历史任务解释和回滚，不重新暴露多套创作入口。

不改端口、数据库表、存储供应商、任务队列架构、ComfyUI 地址和现有工作流节点。若实施发现必须超出此边界，先说明理由与迁移代价，再调整计划。

### 实施时同步文档

- `docs/ARCHITECTURE.md`：新旧合同、来源、输入包、检查边界和迁移。
- `功能说明与扩展指南.md`：追加实施日期、原因、受影响文件、兼容、验证和回滚章节。
- `README.md`：用户可见的写稿、重试、失败原稿与采纳行为。
- `docs/导演台流程与界面结构.md`：流程与文案变化；可见界面变化后更新桌面截图基线。
- `docs/API.md`：实际新增 JSON 字段和错误状态，不写尚未实现的接口为现状。
- 旧恢复计划追加指向本文的实施状态说明，保留原历史结论。

仅制定本文时不修改上述「当前架构」快照，以免把计划误写成已经上线的行为。

### 回滚

暂停创建新合同任务，仅撤回本次入口默认值与相关代码增量；运行中任务按自己的快照完成或由用户取消。保留新合同的只读解释能力，旧代码不得覆盖未知版本稿件。回滚不删除原稿、输入包、历史候选、已采用媒体，不使用整仓 reset 或覆盖其他工作区改动。

如需恢复正式稿，使用已有历史／采纳机制并由用户选择版本；不要用回滚脚本批量替换生产提示词。测试通过不能自动授权采纳，也不能自动升级已存在任务的合同。
