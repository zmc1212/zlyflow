# Director 出片方案：根因与整改方案

日期：2026-09-23。范围：当前工作区代码与已有真实验收记录的只读诊断；本次没有修改生成链路，没有重新调用模型或提交视频。工作区存在尚未提交的功能改动，下述结论以当前文件为准，不以历史版本为准。未统计近期全部生产任务，不能据此断言各种失败的占比。

## 结论

目前最主要的问题是：系统已经有导演设计、结构校验和创作审稿，但还没有形成“明确要求 → 判断能否完成 → 生成 → 按证据修订 → 验证不退步”的闭环。多轮尝试主要是在重复满足复杂约束，并不保证每轮更接近用户要求。

这不是简单加几句提示词、增加重试次数就能解决的。需要同时修复可行性判断、反馈记忆、定点修订和质量验收。生成具有概率性，无法承诺任何素材都一次成功；可以做到的是：可完成的任务有证据地收敛，不可完成的任务提前说明冲突，不再让用户盲目重试。

## 当前代码揭示的具体原因

### 1. 创作审稿发现问题后，没有自动修订闭环

`backend/app/media_studio/services/prompt_expansion_service.py:1576` 调用独立审稿，检查因果、动机、衔接、对白时长、动作密度和摄影表演冲突。但后续只是保存 `creative_review`，把状态设为 `review_required` 或 `reviewed`，随后返回方案。

这意味着“已经知道哪里不好”和“已经修好”之间缺了一步。保存入口主要检查结构有效性；创作审稿问题并不是结构校验失败。前端确实提示“创作质量待人工审阅”，不能说它完全没有区分，但解决问题的负担仍然落在用户身上。

整改：审稿输出稳定的问题 ID、严重度、对应要求、涉及镜头、正文证据和修复目标；修订器修改对应单元，再执行局部校验与全局回归。严重冲突不应默认进入可出片状态，审美建议则允许用户取舍。

### 2. 有些输入在现有限制下无解，却仍进入模型修复

`director_story_design.py:97` 检查正常语速能否说完对白，`:117` 要求每个 Beat 的累计时长保持不变，`:123` 遇换场和容量边界分 Part，`:131` 又要求每个 Part 至少两个单元。同时，每个单元必须拥有事件或对白，禁止无剧情填充。

例如：一个独立场景只有一个不可再分的动作，就可能无法组成当前要求的双段 Part。此时重复生成 JSON 无法消除矛盾。提示词要求“无法拍完写 quality_notes”，但这不能绕过硬校验。

整改：生成前做可行性检查，区分时间不足、单场景单动作、参考图缺失、工作流容量不匹配。输出具体冲突与可选处理：调整时长、明确允许的动作拆分、改用逐镜生成。不要擅自改剧情、加空镜或切换工作流；用户确认过的处理应持久化。

### 3. 当前重试不是有记忆的定点修订

`prompt_expansion_service.py:809` 的修复方式是：原请求 + 本次异常 + 上一次输出，再完整生成；校验通常在第一处异常就抛错。后续轮次不累计全部已发现问题和已解决问题，也不锁定已通过的单元，因此存在“修好 A，又破坏 B”的风险。

`:732` 支持失败 Part 的断点续作，这是应保留的能力。但对已完成、仅创作不满意的任务，重试会重新入队；标准化请求中没有保存用户针对上一版的修改意见和接受项。刷新抽样与持续改善不是同一件事。

整改：分开“故障重试”和“按意见修改”。后者必须带上基础版本、用户意见、锁定项、问题清单与修改范围，返回版本差异。重试若没有减少阻断问题，应停止同一种策略，转为重新规划或明确报告不可满足项。

### 4. 所谓原子事实，部分仍只是按标点切句

`prompt_expansion_service.py:992` 用句号、分号、换行等切分动作事实；持续状态通过少量固定前缀识别。一句“拿信、拆封、阅读后转身离开”仍可能成为一个事件。自然表达的服装、姿态或环境说明，也可能被当成必须执行一次的事件。

之后又要求这些事实完整且各出现一次，模型实际在处理不一定正确的动作边界。`director_story_design.py:103` 还以开场和上一镜落幅文本完全相等判断同场连续性；表述不同不一定意味着画面不连续。

整改：建立结构化剧情表示，区分事件、对白、持续状态、摄影要求和创作偏好，并保留原文位置。状态按人物位置、朝向、左右手持物、姿态等字段比较；程序传递可继承状态，不要求模型反复逐字抄写。

### 5. 导演设计和二次扩写都在描述摄影、表演，容易叠加

`prompt_templates.py:260` 让扩写模型补充运镜、表演、光线和声画细节；`prompt_expansion_service.py:1180` 又将导演设计中的景别、机位、运动、表演和对白时间注入正文，随后追加扩写。

两层内容并非天然冲突，但缺少明确的字段所有权与冲突检查，会增加重复和矛盾风险。当前通过文本替换去掉事实原文，也不能可靠识别语义重复。

整改：摄影、主要运动、动作、表演和状态各有唯一结构化来源；扩写只补指定空缺。程序将最终确认的数据编译成 H3 提示词，避免把规划文本与自由扩写直接叠加。

### 6. 自动审稿和可播放视频都不能证明质量通过

已有 `docs/导演台剧本发展验收记录.md:40` 明确记录：真实预览仍有动作/摄影重复、无参考图却提到参考图 token 的泛化描述，自动审稿没有识别。`:52` 记录实际画面双手持信，与“左手搭桌边”不符。`:42` 已明确写明质量验收尚未通过。

该记录里的文本模型是 `deepseek-ai/DeepSeek-R1-0528-Qwen3-8B`，这只是当时配置，本次未查询当前生效模型。模型能力可能影响复杂约束遵循，但没有同素材、同配置对照，不能把全部原因归结于模型，更不能承诺换模型即可解决。

整改：分别显示结构有效、创作要求满足、成片验证状态。用固定样例比较模型和提示词版本；关键动作要求必须进入实际视频验收，不能只看审稿返回空数组。

## 推荐实施顺序

1. **先让失败可解释。** 汇总最近真实任务，按不可行输入、结构失败、事实错误、创作不满意和视频不遵循分类；记录失败阶段、修复次数、输入版本和生效模型。先建立当前成功率与常见错误基线。
2. **先止住无效循环。** 增加生成前可行性检查；校验返回可修复问题集合；引入用户意见、接受项与修订版本；接上审稿后的定点修订和无进展停止机制。保留现有 Part 检查点。
3. **再整理生成内核。** 将剧情事实、镜头设计、状态连续性和模型提示词编译分层，明确字段所有权；同一数据供审稿、界面、编译和出片使用。旧方案保留，新方案使用明确版本，避免静默改变已采纳结果。
4. **最后证明质量提高。** 固定失败样例集，覆盖长对白、单动作换场、多角色交互、持物连续性、参考图对应及长集分 Part。进行新旧同稿对照，再做远端 ComfyUI 成片抽查；必须读取管理设置中的实际生效远端地址，不切换实例。

## 什么才算解决

建议采用以下验收门槛，作为后续实施目标，而不是宣称当前已经达成：

- 确定性约束：剧情和对白不丢不重、参考图映射正确、已锁定要求不被返修破坏；验收样例中全部通过。
- 不可行任务：在昂贵生成前给出具体冲突和处理选择，不反复返回同一类“请重试”。
- 修订效果：每轮报告解决、遗留、新增的问题；已解决问题不回归，无改善时改变策略或停止。
- 文本质量：人工按忠实度、因果、节奏、表演摄影一致性和可拍性进行同稿对照。记录首轮可接受率、两轮内可接受率、耗时与调用成本；依据基线约定提升目标。
- 视频质量：关键动作、持物、人物身份、时序和对白分别核验；“生成成功、能播放”只算技术链路通过。

最优先的改造是“可行性检查 + 带意见的定点返修 + 审稿后再验证”。它直接对应目前用户反复尝试却不收敛的问题。结构化内核与真实回归样例用于防止今后继续通过堆提示词修补同类问题。
