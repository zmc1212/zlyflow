# 资产提取与镜头规划接入开发计划

日期：2026-09-28  
状态：推荐方案，待实施；本文不代表功能已接入或模型效果已验收。  
关联调查：[镜头人物遗漏根因分析](镜头人物遗漏根因分析-2026-09-28.md)。

## 1. 目标与范围

将两份用户指定文档分别用于全局资产提取与镜头规划，建立剧本、资产、镜头之间可追溯的关联，解决人物已写入剧情却未进入镜头资产列表的问题。

指定来源：

- 资产提取：`skills/AI短片全流程/【资产库】全资产大师V3.0_场景+角色+道具_万能版.txt`。
- 镜头规划：`skills/AI短片全流程/分镜解析公开版.md`。

本次计划包含提示词适配、资产清单版本、镜头资产关联、衔接修订后核对、页面候选确认、旧项目迁移和测试。不重写已采纳故事，不改现有视频模型节点，不引入新 ComfyUI 实例，不自动重新生成角色图或视频。资产卡生图文案与镜头 H3 正文沿用各自职责，不混入本次拆镜输出。

## 2. 当前基线与问题

| 环节 | 当前入口或代码 | 现状 |
| --- | --- | --- |
| 剧本扩写 | `script_development.py` | 分集生成结果附带简要 `assets` |
| 采纳剧本 | `script_development_service.py::apply` | 汇总分集资产到文档分析结果 |
| 同步资产 | `project_detail_service.py::transfer_assets_from_document` | 根据文档资产创建或同步项目资产 |
| 内容库规划 | `LlmService.plan_episode_shots` | 拼接代码内提示词，按场景规划，再做衔接修订 |
| 工坊规划 | `workshop_service.py::run` | 可以重新规划，也可以复用既有镜头只调整分组 |
| 资产关联 | `_beats_from_document_shots`、`workshop_references.py` | 主要相信已有角色名及绑定 ID |

已确认本例扩写原稿包含沈砚和母亲，内容库第 8 镜的动作包含沈砚，但 `characters` 仅有母亲。衔接修订可改动作、开场和收束，却不允许修改人物数组；修订后缺少一致性核对。历史任务没有逐阶段原始响应，无法确定首次矛盾发生于初稿还是修订。

本方案既补齐上游资产清单，也修复逐镜关联与最终核对；只换提示词无法构成完整修复。

## 3. 推荐流程

```text
已采纳剧本与项目设置
  ↓
全资产大师：生成全局资产候选与出处
  ↓ 用户确认差异、复用或新建资产
已确认资产清单版本
  ↓
分镜解析：剧本 + 相关资产清单 + 项目约束 → 镜头候选
  ↓
衔接修订：动作、姿势、空间和时间连续性
  ↓
逐镜资产核对：可见人物 / 画外发声 / 提及人物 / 场景 / 道具 / 造型
  ↓ 结构校验；有歧义则保留候选并提示确认
用户确认镜头与分组
  ↓
工坊素材 → H3 写稿 → 提示词确认 → 视频生成
```

资产提取以完整采纳剧本为依据；长剧本按分集提取、全局合并身份与别名，必须显示覆盖范围，禁止静默截断。拆镜使用当前分集/场景全文与相关资产清单，资产筛选不可只依据旧镜头的人物数组，否则会再次过滤掉遗漏角色。

## 4. 提示词接入策略

保留两份原始文件不改写。新增独立适配模块，按明确章节构建运行时提示词；任务记录来源路径、文件 SHA-256、选用章节、适配版本与实际发送内容。不能只保留“使用了某技能”的标签，也不能拼上相互矛盾的规则后期待模型自行判断。

规则优先级：用户已确认的剧情、对白和项目设置 → 当前工作流真实能力与接口合同 → 阶段适配规则 → 原文中的创作方法与示例。示例只作参考，不得把机甲样片等内容带入用户故事。

### 4.1 全资产大师：用于清单提取

保留全剧扫描、角色/场景/道具分类、具名角色独立成卡、时代与造型区分、不遗漏有剧情功能资产及交付自检。

适配项：

- 四问所需画风、时代、参考风格、资产范围优先读取项目设置；真正缺失且影响结果时才在页面补充。
- 本阶段输出结构化资产清单与原文出处，不生成数百字生图卡；详细生图描述留给资产库后续操作。
- 删除运行时“场景必须有氛围人物”的强制要求。只有剧本有依据才提取群像，不能凭场景类型发明人物。
- 不强制真人写实，沿用工程画风；跨时代人物以同一角色的不同造型记录。
- 外观未知项标为未明确，不将推测当成剧本事实；艺术补充需要单独标识。
- 正文中的称谓、别名与姓名合并必须有证据，冲突形成待确认项；不自动把“母亲”与多个家庭中的母亲合并。

### 4.2 分镜解析公开版：用于镜头设计

优先选用视听签名、单元化、镜头卡、机位/运镜/转场、自检及角色可视镜头出处规则。VFX 公司推荐、传统制作预算、营销标记配额和长篇完整样片不进入默认运行时上下文。

适配项：

- 不重排或改写已采纳故事与对白，不擅自增删情节、人物和集数。
- 保留拍摄设计能力，但不机械套用“每单元 5–12 镜”“对白后必有反应镜”等配额。
- 输出后端约定的 JSON，界面可以展示表格；Markdown 七列表不能直接充当持久化协议。
- 每镜补充角色、造型、场景和道具引用、出现方式与证据，不仅提供一句内容摘要。
- 当前首期仍按现有可生成镜头单元工作：规划阶段的时长须与当前工作流限制一致，不直接输出 0.3 秒闪剪后由程序强行拉长。原文 1–8 秒或剪辑 ASL 仅作方法参考。若后续开放短剪辑镜头，须单独设计“剪辑镜头—生成片段”映射，不混入首期。
- 画幅、时长和参考图数量限制以 `workflow_registry.py` 及当前工作流为准，不能在新模块重复维护一套能力表。

### 4.3 最终资产核对

输入原场景、已确认资产清单及衔接修订后的完整镜头。必须覆盖静默角色、被看者、背影、局部出镜、开场/收束才出现的人物，区分画外发声、只被提及和画面中实际出现。

核对阶段只提出关联修订和歧义，不偷偷改写剧情、对白、镜数或机位。需要改变画面设计时回到镜头候选修订。存在语义矛盾时最多进行一次有证据的纠正重试；仍不明确则待用户确认，不能无限循环或静默放行。

姓名匹配只能用于发现疑点，不能作为最终出镜判断。模型核对也不保证正确，页面必须能展示证据和修改结果。

## 5. 数据与一致性合同（拟定）

首期优先复用现有文档 `analysis_json`、分集 `data_json` 和任务 `payload_json`，不新增业务表。以下为拟定字段，落地前需核对现有同名字段和任务框架。

| 对象 | 必要信息 |
| --- | --- |
| 资产清单版本 | schema 版本、来源文档/剧本版本及哈希、覆盖分集、资产条目、候选/已确认状态、确认人和时间 |
| 资产条目 | 稳定清单 ID、类型、规范名、别名、时代/造型、原文证据、已有项目资产 ID 或待创建标记 |
| 镜头资产引用 | 清单 ID、实际资产 ID、造型 ID、可见/画外发声/提及类别、所在动作或起止状态、证据及人工确认状态 |
| 任务证据 | 输入版本、模型与参数、提示词源哈希、实际请求内容、原始响应、解析结果、阶段检查点、重试记录 |
| 核对结果 | 通过/待确认/失败、漏项、冲突、建议修订、对应镜头与来源证据 |

兼容规则：

- `characters`、`character_ids`、`character_look_ids` 等现有字段继续服务下游，由确认后的引用投影得到，避免同时维护两套互相冲突的名单。
- 模型只能引用输入清单中的稳定标识；项目数据库 ID 由服务端校验和映射，不采信模型凭空生成的 ID。
- 全局清单存在某人，不等于每镜都出镜；画外声音和对白提及不会自动占用人物图片槽位。
- 资产已提取但图片未生成，仍允许完成镜头规划；进入需要图片的写稿/出片阶段再使用现有素材就绪检查。
- 参考图超限必须显示冲突、拆组或明确选择，不截断人物。手工参考与已确认人物不一致时要求明确处理，不能默用另一人的图。
- 剧本或资产清单变更使相关候选过期。采纳时同时检查来源版本、资产清单版本、规划 revision 和参考指纹，防止迟到响应覆盖新数据。
- 关联或参考改变后保留旧提示词和视频，按既有指纹机制标记提示词待更新；不能修改旧指纹把旧稿伪装成新稿。
- 原始响应和快照复用任务存储，须评估长剧本体积并做列表轻量投影；不把凭据或供应商密钥写入证据。

## 6. 页面接法

沿用导演台现有内容库、资产库和工坊布局，不重做项目壳。

### 内容库

在已采纳剧本操作区提供“提取全局资产”与状态，完成后展示候选清单、原文出处和相对已有资产的新增/复用/冲突。确认后建立资产清单版本；详细图片仍由资产库生成。

“规划镜头”读取已确认清单。尚无清单时引导先提取，保留当前页面；不自动覆盖旧资产。任务进度区分“镜头规划 / 衔接修订 / 资产核对”。

### 镜头候选

在当前候选展示中增加人物及造型、场景/道具和待确认标记；展开可看出处。人物与动作矛盾时，不以“任务完成”掩盖问题；须确认或修订后采纳。

### 工坊

重新规划和“保留当前镜头，只调整分组”共用核对入口。分组本身不应触发重新创作；只有旧镜头尚未核对或版本已变化时补核对。素材页显示缺失绑定及入口；提示词因关联变化而过期时沿用当前提示反馈。

所有新表格、选择器、弹层和反馈使用 Ant Design；保持根级双主题。只验桌面端，在 5173 实页检查。本计划不改导演台对话创作室样式；如果实际实现触及该区，再按项目规则对照官方组件源码。

## 8. 分阶段实施与交付门槛

| 阶段 | 工作与产物 | 完成条件 |
| --- | --- | --- |
| P0 合同冻结 | 核对当前路由、资产合并和任务协议；确定 JSON、版本、错误分类及测试样本 | 两份提示词的保留/覆盖规则可审阅，单镜与生成单元定义明确 |
| P1 全局资产提取 | 提示词适配、提取任务、清单候选与确认、资产库复用 | 同一剧本重跑不重复创建；人工图片及造型不被覆盖；遗漏/别名冲突可见 |
| P2 镜头规划 | 分镜解析适配、原文+资产清单输入、结构化镜头候选 | 剧情对白完整，工作流约束正确，角色引用可映射 |
| P3 最终核对 | 衔接后资产核对、证据和待确认状态；所有入口共用 | 双人镜不漏静默角色；画外/提及不会被强加出镜；旧稿正确失效 |
| P4 页面与旧项目 | 候选确认、版本反馈、旧数据扫描与可回退修复 | 不自动重拆整集、不覆盖已有视频，用户能看见每项变更 |
| P5 对照验收 | 测试、实际模型对照、桌面回归、文档同步 | 工程验证和创作效果分别出具结果，通过后再默认启用 |

按 P0 → P1 → P2 → P3 → P4 → P5 执行。首期不扩大到剪辑时间线重构、跨镜自动合成或资产图片重生成。

## 9. 测试与效果验证

### 工程回归

后端测试放 `backend/tests/`，前端测试放 `frontend/src/**/*.test.ts(x)`。

- 提示词：来源哈希、章节选择、结构化输出、项目设置优先级、未知字段与坏 JSON。
- 资产：别名、重名、跨集同人、现代/古代造型、群像、无图资产、已有人工图片保护及重复确认幂等。
- 镜头：母子双人/静默人物、只露手或背影、画外声音、对白提及、代词指代、开场/收束人物、衔接修订导致人物变化、跨场不继承演员。
- 一致性：未知资产 ID、版本过期、候选迟到、人工绑定、超参考上限、取消/重启/重试、确认事务失败及旧稿失效。
- 界面：候选差异、证据展开、歧义确认、错误状态及未保存修改保护；浅暗主题桌面验证。

拟用命令：

```powershell
python -X utf8 -m unittest discover -s backend/tests -p "test_episode_shot_planner.py"
python -X utf8 -m unittest discover -s backend/tests -p "test_workshop*.py"
python -X utf8 -m unittest discover -s backend/tests -q
pnpm --dir frontend build
git diff --check
```

新增专项测试随模块命名补入命令。构建走 `pnpm build`，不直接运行 `vite build`；仅在阶段验收构建，日常页面检查使用 5173。截图与日志放已忽略的 `test-results/`，验证后清理，不写根目录或业务源码目录。

### 实际模型对照

使用相同剧本版本、模型、参数及资产库快照，对比旧链路与新链路；每次保留实际输入、响应与核对证据。覆盖本集第 8 镜、第 23 镜及人工构造的画外人物等反例。至少进行三次重复运行，避免以单次成功宣称稳定。

人工标注每个样本的预期可见角色、画外角色、提及角色和正确造型。报告漏人、误加人、造型错误、对白遗漏、待确认率、模型调用次数、耗时与费用。

首期验收门槛：关键回归样本不得漏已明确出镜的角色、不得错绑身份；明确画外/提及样本不得误加可见角色；歧义必须显式待确认；不得新增或改写剧情对白。若达不到门槛，保留候选模式，不默认启用。不要以增加待确认次数代替提升正确性。

本轮提示词/规划验收不必生成视频。后续若做成片验收，先读取管理设置实际生效的远端 ComfyUI 地址，只针对该实例操作，不切换配置或启动本机实例；视频结果与规划检查分别记录。

## 10. 旧项目迁移与回滚

不在 GET 请求中自动重写历史数据。旧项目保留可读，以“待核对”区分未执行新流程的数据。

对本项目先生成变更预览：第 8 镜补沈砚的古代造型，核对第 23 镜是否实际拍到母亲；其他镜头不按姓名扫描结果直接批量修改。确认前保存原关联、组参考、提示词与版本证据；确认后只更新确定范围，旧稿标过期、旧视频保留。不要为修复一个镜头重新规划整集。

回滚分两层：关闭新链路入口或恢复旧实现；已采纳数据通过保存的版本恢复，不能仅回退代码丢弃新字段。回滚不得删除资产图、任务或视频，不得重新认可已经因参考变化而失效的稿件。新旧数据读写兼容必须有测试。
