# 导演台与 Codex 提示词生成链路差异

## 核心判断

目前不能把差距归结为“同一个 skill，GPT-6 比 DeepSeek 写得好”。核查发现，导演台的实际模型路由、skill 加载内容、上下文、写作权限、输出格式和质量检查都存在独立差异。

最关键的两点是：**带参考图的这条路径默认会让视觉模型直接写稿；导演台也没有加载项目中那份动作、语气、台词细化 skill。** 因而目前不是控制变量的模型对比。

以下依据 2026-09-26 当前代码、当前供应商配置，以及 `job-87185bbc7add` 的历史输入快照。没有发起新的 LLM 或视频生成，没有改动业务代码、供应商或项目数据。离线复现仅在独立 Python 进程内用捕获函数替换 LLM 调用，提取组装结果后立即退出。

## 1. 实际写稿模型可能不是 DeepSeek

只读查询到的当前配置：

| 配置项 | 值 |
| --- | --- |
| 文本 LLM | `deepseek-v4.1-flash`，启用 |
| 视觉 VLM | `glm-4v-flash`，启用 |
| LLM reasoning_effort | `low` |
| 当前代码是否把上述 DeepSeek 识别为视觉模型 | 否 |
| 当前代码是否把上述 GLM 识别为视觉模型 | 是 |

`workshop_group_prompts.py:41`：有参考图就调用 `LlmService.chat_vision()`。

`llm_service.py:394`、`:559` → `vision_runtime.py:224`、`:336` 的逻辑是：

1. 如果文本 LLM 被识别为支持视觉，直接由它看图写稿。
2. 否则，如果配置了可用 VLM，**把整个 system、user 和参考图交给 VLM，直接输出最终稿**。
3. 视觉调用出错，回退文本 LLM；没有视觉端点时也走文本路径。

这并不是“GLM 先看图提取事实，再由 DeepSeek 负责创作”的两阶段流程。

该镜头组有四张参考图，所以按当前配置和代码，正常路径是 `glm-4v-flash` 写稿，异常回退才可能用 `deepseek-v4.1-flash`。这是本次最值得先查清的模型差异。

**历史证据限制：** 两个相关提示词任务未保存实际模型和视觉回退元数据；`chat_vision()` 接到了 `_meta` 却只返回文本。当前配置的更新时间早于这两个任务，但这仍不足以证明当时一定成功走了 GLM。准确说法是“当前路由指向 GLM，历史实际响应模型无法从任务记录确认”，不能把猜测写成定论。

## 2. 系统实际加载的 skill 与你以为的可能不是同一份

当前整组写稿实际加载：

`backend/app/h3_prompt_writing/SKILL.md`

但不是完整注入。`llm_minimax_skills.py:838` 只摘取 `Workflow`、`Output Rules`、`Tips` 三类章节。当前全文 2,618 字符，摘要 1,220 字符。

项目里另外有：

- `skills/MINIMAXH3格式动作语气台词细化SKILL/SKILL.md`
- `skills/minimax-h3-director-segment-prompt/SKILL.md`

它们明确要求 `subject_definitions`、声音设定、`<d>[中文]…</d>`、`(S1)`、动作带语气、`【主体】/【动作】/【镜头】/【音效】/【约束】`。这些与对照 txt 的结构高度一致。

**当前 `generate_group()` 路径没有读取这两个文件。** 重构计划中写了要用动作语气细化 skill，不等于当前运行代码已经接入。

不能仅凭输出结构倒推 Codex 当时究竟读了哪个文件；尚未取得那个 Codex 任务的完整生成记录。如果你当时用的是上述动作语气细化 skill，就可以明确说两条路径没有使用同一份 skill。

## 3. 摘要要求“读指南”，API 调用却没有给模型读文件的工具

摘要保留了“Ref2VA 读取 `references/ref-en.txt`”的指令，但此路径没有加载该文件，也没有向模型提供读本地文件的工具。

`references/ref-en.txt` 当前有 23,551 字符，其中明确写了统一 `(S1)` 等声音来源编号、`<d>[Language] …</d>` 对白形式及完整示例。只把本地相对路径写进消息，不会让远端模型自动获得文件内容。

这是 skill 从 Codex 代理环境移植为普通 API 调用时容易出现的缺口：**代理能按指令继续读参考文件；这里的请求只发两条消息，读文件动作没有实际执行。** 本次没有证据证明 Codex 当时读了所有指南，但系统这条路径未注入它们是明确事实。

离线以历史任务快照调用当前组装函数，在真正请求前捕获到：

| 请求内容 | 结果 |
| --- | --- |
| system 长度 | 3,900 字符 |
| user 长度 | 4,479 字符 |
| 参考图 | 4 张 |
| temperature / max_tokens | 0.2 / 24,000 |
| system 或 user 是否包含 `<d>` | 否 |
| 是否包含 `(S1)` | 否 |
| 是否包含 `【约束】` | 否 |
| 是否包含 `references/ref-en.txt` 路径 | 是，但没有正文 |
| 是否包含整集原始剧本文本 | 否 |

所以对白标记没生成，并不能直接作为模型能力差的证据：这次请求没有明确教给它这些要求。

## 4. 毛笔错误来自上游输入，并被系统锁定

历史提示词任务 `job-87185bbc7add` 的 `base_plan` 里，公共设定在调用模型前就已经是：

> `<Subject 4>：毛笔，以 <Picture 4> 为外观权威参考。`

四个参考槽名称依次是沈砚、台灯、笔记本、毛笔。生成器随后要求“公共主体及声音设定保持不变”，标签规则又要求不得漏掉或交换既有参考。

因此“现代图书馆变成用毛笔记录”至少在这轮不是模型凭空想出来的；它在按上游资产与锁定设定写。换更强模型可能发现冲突，但在当前约束下也可能继续忠实使用毛笔。

对照 txt 则明确使用钢笔，只声明一张人物参考图。即便真的给同一个模型，这两份输入也会合理地产生不同画面。

## 5. 系统允许模型发挥的范围更窄，公共设定的新内容还会被丢弃

`generate_group()` 用 `rewrite_mode="strict"`，要求不能改剧情、对白、镜头数量和各镜时长，也不能变更公共主体及声音设定。

它要求模型为每镜生成六段式文本，但 `workshop_group_prompts.py:49` 随后明确排除 `subject_definitions`，只保存其余五段。最终视频沿用组里原有的 `common_prompt`。

这意味着：即使模型在主体定义中补写了更明确的声音、服装、摆位等信息，只要没有同时写进保留的部分，新增内容也不会进入保存的镜头正文；公共设定不会被这次生成自动升级。

这不能证明历史原始响应里实际包含了更好的定义，因为原始完整响应未保存。能证明的是，当前设计存在这样一个信息丢失出口。

对照 txt 则把共享场景、人物参考边界和同一说话人直接写在最终文本中。它不受这一步裁剪。

## 6. 上下文和交付目标不一样

导演台将当前组公共设定和该组完整 beat 数据序列化后发送，包含动作、镜头、音效、原有简短提示词、时长等。当前组是三镜 24 秒。

历史任务虽保存了整集来源剧本，但 `generate_group(plan, group, beats)` 只使用组设定与组内镜头，不把完整来源文本、Codex 对话里的修订意见或其他历史创作上下文自动发送给模型。

对照 txt 是两镜 16 秒，按一条连续时间线编写。它特别强调“不提前引入古籍异动”、匹配切点、动作动机和物件摆位。系统有开场/收束字段，也有一句总括的连续性要求，不能说它完全没有上下文；但没有对照文件那样具体的执行指令。

**独立镜头从零计时本身没有错。** Director 时间轴会把它们顺序排列。真正需要改的是跨镜状态与表演细节，而不是把第二个 segment 生硬改成累计时间。

## 7. 多层指令存在不一致

本次捕获的消息同时包含：

- 中文模板：必须输出中文六段式；摘要 skill：正文使用英文。
- 摘要 skill：目标长度 4–15 秒；用户消息：整组 24 秒。
- 基础模板：只返回干净六段式文本；追加 system：改为 JSON `shots` 数组，每项再嵌六段式。
- 原始素材是事实边界、严格改写；同时又要求导演设计、细节可执行，但没有明确区分“可补的表演细节”与“不可改的剧情事实”。

JSON 覆盖和本地时间要求是有意设计，不是它们天然降低质量。不过这些叠加要求没有被整理成一份统一任务说明，增加了解释负担，也使模型更可能优先完成结构、编号和字面复述。

## 8. 验收偏格式，没有检查“是否演得出来”

`workshop_contract.py:127` 的主要检查是：

- 内容不为空；
- Picture 编号合法，Subject 已定义；
- 原台词字符串没有遗漏；
- 镜头标记符合 `[Shot 1]`；
- 时间范围从零开始，终点等于该镜时长。

它没有校验一句台词的子时间窗是否足够，没有要求统一说话人和对白标签，也没有检查毛笔与现代场景的矛盾、图片不能定义音色、手部动作与说话是否过于拥挤、是否明确匹配切点。

因此，“3 秒念完长句”也能通过，只要外层镜头依然是 8 秒。整组路径成功返回候选后，没有独立的表演质量审稿与修复循环。人可以在采纳前检查，但程序没有保证这些创作质量条件。

## 9. 推理和采样不能简单等同

当前写稿指定 `temperature=0.2`、`max_tokens=24000`；只发送 system 与 user，不包含 Codex 那次任务的完整交互过程。

虽然配置里 reasoning_effort 是 low，当前 `chat_on_endpoint()` 只对 `is_openai_reasoning_chat_model()` 命中的模型发送该参数。该识别函数当前识别 GPT-5 和 o1/o3/o4，不命中上述 DeepSeek 或 GLM。因此不能说 DeepSeek 这次“确定用了 low 推理”，只能说代码没有通过这个字段显式配置它的思考模式；服务端如何处理仍需请求日志核实。

同样，没有 Codex 原任务记录，就不能断言 GPT-6 当时用了什么推理档位、读了多少资料或返修了几轮。不应拿未知的两种执行条件推导模型能力排名。

## 原因优先级与建议

| 优先级 | 原因 | 处理方向 |
| --- | --- | --- |
| 最高 | 有图后可能切到 GLM 完整写稿，实际模型不透明 | 保存每次请求的实际模型、路由、视觉状态与回退原因；明确谁负责看图、谁负责创作 |
| 最高 | 动作语气 skill 没接入，详细指南没发送 | 明确唯一有效 skill，实际加载必要正文和示例，不能只传路径 |
| 高 | 上游毛笔参考错误且被锁定 | 写稿前做时代、资产与剧本一致性检查，把冲突作为待修正输入 |
| 高 | 公共定义被冻结，新主体定义被裁剪 | 分离公共设定生成与镜头生成，或者明确所有新增共享信息的保存与提交位置 |
| 高 | 只校验格式，不校验表演与说话节奏 | 增加对白时间预算、动作密度、说话人、匹配切及语义一致性审稿 |
| 中 | 指令冲突、上下文与交付范围不同 | 统一语言/格式/时长规则，提供必要前后镜状态，清理重复和无关字段 |
| 待实验 | 模型本身的细节理解、表演设计与指令执行差异 | 上述条件一致后，再比较 GPT 与 DeepSeek 的结果 |

建议先修生成链路，再判断是否必须升级模型。否则即便换成 GPT，仍可能收到毛笔输入、看不到 skill 参考指南，并被程序丢弃新增主体定义。

做模型对比时应固定同一份 system、user、参考图、组范围和输出结构，并确认实际响应模型；做链路对比时则固定模型，只切换旧版与完整技能版。不要同时换模型、改参考图、改提示词结构、改视频参数，否则仍无法判断改善来自哪里。

目前可明确回答：**有，而且不止模型。最实质的差别是“可能不是你配置的文本模型在写、没有加载你期望的那份完整技能、上游错误被锁定、输出被裁剪、验收不检查表演质量”。**
