# 导演台“生成预览”根因与完整修复方案

日期：2026-09-23。对象：`proj-0f9c8015281149f0` / `ep-4d89a8df80a4`。状态：只读诊断完成，以下实施方案尚未执行。

## 结论

问题来自整条方案生成链路，不是简单的网络不通或 ComfyUI 不工作。当前最严重的缺陷，是分集详情接口把剧本每个非空文本行直接保存成分镜，然后要求模型对这些错误的“剧情事实”逐项保真；下游又要求每个场景至少组成两段，缺字段时整集重写，失败后丢弃原始输出。

因此，只改提示词、增加重试次数或换模型，都不能完成根治。需要修复输入契约、结构化生成、分段编译和任务恢复；模型升级只能作为经过真实样本测试后的补充。

### 2. 当前输入已经被错误结构化——最高优先级

最新任务快照：

- `台词：沈砚：“这篇古文，到底是谁写的……”` 也在动作字段中，没有对白归属。

直接代码来源：`backend/app/media_studio/services/project_detail_service.py:1801–1827`。

`get_episode_detail()` 在没有结构化 shots 时，把 `script_text.split("\n")` 的每个非空行构造成 shot，并执行数据库 UPDATE。用户只是打开详情，就可能把“文本兜底”永久写成生产分镜。

事实构建随后读取动作字段并分配稳定 ID（`prompt_expansion_service.py:1072`）；前置校验检查事实数量和时长，却不识别标题、人物列表和对白字段错位。因此最新输入的 `preflight` 返回空问题列表。所谓“完整覆盖事实”，实际要求模型覆盖剧本标题等非镜头内容。

### 3. 公共设定契约没有可靠保障

`director_story_design.py:26–47` 用文字要求模型一次返回公共设定、全剧镜头单元、状态、事实 ID、时长、机位和表演；`pack_design()` 在第 60 行要求 `common_setting.subject_definitions` 非空。

最近一次请求重建后的用户提示约 47,913 字符，其中资产 JSON 约 29,071 字符，带入 41 个资产；实际选择的参考槽位为 9 个。该数字是字符数，不是 token 数，也不能据此断言发生了上下文溢出。

`LlmService.chat_text()` 使用普通流式文本调用，当前该路径没有传递 JSON Schema / `response_format`；请求固定上限 16,000 输出 token、300 秒超时。大型自由文本响应要一次满足多种结构与业务约束，脆弱性较高。

当前配置读取为 SiliconFlow 的 `deepseek-ai/DeepSeek-R1-0528-Qwen3-8B`，但失败任务没有保存每次调用的模型配置快照，不能断言全部历史失败由这个模型产生，也没有证据证明更大模型一定解决问题。

**证据边界：**历史失败任务不保留原始返回文本，无法判断是漏字段、字段改名、错误嵌套还是空值。可以确认的是校验失败位置和容错机制不足，不能虚构模型当时的返回内容。

### 4. 单镜场景被产品规则拒绝

`director_story_design.py:121–133` 按场景变化、段数和帧容量分组，每个 unit 直接映射为一个 segment。某场景只有一个 unit 时直接报“至少两段”。

这混合了三个不同概念：剧情动作单元、视频提示词段、视频提交批次。一个完整动作只适合一个镜头，并不意味着剧本错误。

另一个风险是场景边界使用模型生成的自由文本 `scene_key`；同一地点的不同措辞或镜头局部位置可能触发不必要的切分。已有失败中的“茅屋”“茅屋内米缸旁”需要结合空间与时间判断，不能仅凭字符串决定连续性。

当前测试甚至明确期待短场景报错；这说明现象是已编码的限制，而不仅是随机模型不配合。

### 5. 重试与恢复放大问题

- `prompt_expansion_service.py:895–918`：每次完整重发原输入和上次输出。只缺一个公共设定字段也重写整集，既重复花费又可能引入新错误。
- 同一错误文字重复出现就设置 `DIRECTOR_NO_PROGRESS`、`retryable=false`；随后 `retry()` 第 796 行拒绝局部重试。缺字段与真正不可满足的输入冲突没有被合理区分。
- `prompt_expansion_service.py:1016–1035`：失败时 `pop("stream")`，且首阶段通过前不保存设计草稿，导致失败原文和部分成果丢失。
- 任务用 API 进程内 `ThreadPoolExecutor` 执行；服务重启后恢复逻辑会将活动任务标为失败。数据库记录证实发生过多次中断。
- `recover_interrupted_jobs()` 查询共享数据库中的全部活动预览，没有 worker 所属范围和租约判断；多实例环境还存在把其他实例任务误判为孤儿的风险。该风险由代码推导，未证明它是此次重启失败的实际触发方式。
- 前端刷新时恢复的是活动任务；“查看最近预览”只寻找已完成任务。失败卡缺少同等的持久化恢复入口，容易回到用户截图所示的空面板。

## 二、完整修复设计

目标流程：

```text
剧本原文 → 结构化场景/动作/对白 → 输入检查与资产绑定
        → 公共设定锁定 → 分场导演设计 → 程序编译与容量规划
        → 分段创意扩写 → 结构校验/创作审稿 → 可查看预览
        → 确认采用 → 按计划提交视频 → 时间线合成
```

### P0：先修输入，停止生成错误事实

1. 删除“每行即分镜”的生产兜底。没有已规划分镜时返回 `needs_planning`，展示原文及“规划镜头”，不能显示“脚本就绪”并允许继续生成方案。
2. 标题、摘要、人物表只作为元数据；场景、时间、人物、动作、对白、说话人要分别建模。`台词：无` 表示空对白，不是事件。
3. 对已识别的剧本格式使用明确解析器；不确定格式进入结构化抽取及复核，不能伪造已完成分镜。每个事实记录原文位置和来源版本。
4. 场景使用稳定 ID、时间和空间关系。角色别名与身份造型显式映射，无法唯一匹配时展示待确认项，不能猜测“母亲”对应哪个资产。
5. 将分镜准备状态、剧本修订号、来源校验结果写入数据契约。检查标题被当动作、对白全部错位、目标时长冲突和未绑定身份等情况。
6. 详情读取不再负责创建生产分镜；解析和规划由明确的写操作完成，避免浏览页面改变创作数据。

### P0：公共设定独立生成，模型不负责复制机械字段

1. 从选中资产及必要背景编译稳定的参考槽、名称、身份、造型约束；公共设定作为独立小步骤生成并立即保存检查点。
2. 接口统一定义 schema；模型支持结构化输出时使用 schema 约束，不支持时仍执行严格解析与字段校验。不能假设所有兼容接口支持相同参数。
3. 分场设计仅输入相关事实、已锁定公共设定、简短全局剧情和相邻交接状态；不重复传全部 41 个资产及不相关数据。
4. 事实 ID、引用槽位、Shot 编号、时间边界、固定连续性语句和确定性的状态传递由程序编译。模型负责有创作价值的镜头组织、表演和运镜。
5. 已知、安全的结构差异可做版本化规范化；不得通过空公共设定、随意补剧情或关闭保真校验使任务“假成功”。

### P1：统一制作计划，支持单镜和连续段

推荐将创作计划与执行工作流分开：每个渲染单元包含来源事实、镜头设计、时长、参考图和 `render_kind`。

- 同场、确需连续生成且满足工作流能力的多段，使用 Director 工作流。
- 独立单镜或不足 Director 最小段数的短场景，使用现有普通 H3 工作流适配器。
- 跨场景明确切换，在时间线合成；不能为满足两段限制强行假装连续。
- 一个剧情单元是否需要多镜覆盖应由动作和摄影设计决定，不能为凑数拆对白、重复事件或补无意义空镜。

**实施边界：**这是需要开发的执行适配能力，当前前端切换工作流并不等于已经支持混合计划。必须同步修改生成、采用、选段、任务快照和合成逻辑，验收通过后才能上线。

容量规划从 `workflow_registry.py` 读取约束，区分 unit、shot、segment、part。采用可回溯分组或动态规划处理边界，先证明不可行再报错。目标“9 段”定义为偏好，明确展示实际段数及差异原因；不承诺任何剧本都能严格变成 9 段。

若第一阶段尚未完成混合渲染，预览仍应能展示完整创作计划并标出待适配单镜，禁止把未实现的执行路线标成“可直接出片”。

### P1：按错误类型修复，保留每一阶段成果

| 错误类型 | 处理方式 |
|---|---|
| JSON 语法、字段缺失 | 只修当前结构或字段，冻结已验证数据 |
| 响应截断 | 保存 finish reason / 用量，缩小输入或分块续做 |
| 场景身份、时长、事实冲突 | 调整对应规划，展示具体原文证据 |
| 单镜不满足 Director 容量 | 选择单镜执行适配器，不重写剧情 |
| 429、可恢复超时或 5xx | 有上限的退避重试，只重跑当前调用 |
| 模型不存在、鉴权失败 | 配置层错误，不进入创作修补循环 |
| 服务中断 | 从有效检查点恢复，已经成功的部分不重复请求 |
| 审美与节奏建议 | 显示建议和返修入口，与结构错误区分 |

限制每阶段调用次数和总耗时；“不再自动重试”与“用户修复条件后不可重试”必须分开。只以错误字符串相同就永久锁死，不足以表达可恢复性。

结构有效、仍需创作修订的方案可以查看，并保留意见；涉及事实、引用和不可执行内容时保持出片门禁。无法解析的响应只能显示为诊断草稿，不能当成有效方案采用。

### P1：持久化任务与可追溯诊断

1. 将长任务移出会随开发热更新重启的 API 进程，建立持久化 worker 调度。
2. worker 领取使用原子操作，并保存 owner、lease、heartbeat、attempt；只能回收租约过期任务，旧 worker 的迟到结果不能覆盖新结果。
3. 检查点细分为源快照、公共设定、各场景设计、编译、各段正文、审稿、采用；每个检查点绑定输入指纹和 schema 版本。
4. 每次调用保留模型/供应商标识、模板版本、阶段、耗时、截断原因、校验路径、原始草稿和修补差异。API Key、鉴权头不进入日志；正文诊断按项目授权访问并设保留期限。
5. SSE 只负责实时显示，数据库状态是事实来源。刷新后恢复最新任务，包括失败、待修复及完成状态。
6. 防止双击重复入队；请求幂等键覆盖项目、剧集、来源版本、生成参数和阶段。

### P2：真实模型能力验收

使用当前真实剧本样本验证结构遵循、对白保真、规划质量、长输入表现、耗时及费用；依据结果选择配置中的合适模型。不要在模型尚未验证前把稳定性寄托于模型名称或参数规模。

保留较小模型处理简单抽取的可能性；是否分模型由测量决定。供应商切换应显式记录，失败任务必须知道当时实际调用了谁。

## 五、必须满足的验收标准

1. **真实输入回归**：当前六场剧本不会产生标题镜头、人物列表镜头或“台词：无”镜头；实际对白进入对白字段并有说话人与原文位置。
2. **输入门禁**：未规划剧本、错位对白、时长冲突都不能伪装成已就绪；但问题必须可定位和修复。
3. **公共设定**：缺字段、错误嵌套、空值、JSON 截断都有明确分类；只修对应阶段，已完成场景不重复生成。
4. **合法短场景**：单镜场景有真实可执行的路由，不靠重复动作、删校验或假连续通过。
5. **容量边界**：满足注册表的段数、帧数和参考图限制；可行分组不被贪心余数误拒；不可行时返回具体约束冲突。
6. **恢复**：刷新页面、关闭页面、SSE 断线和 worker 重启后恢复一致状态；另一实例启动不能打断活动任务；重复点击不产生重复任务。
7. **来源一致性**：生成过程中修改剧本、造型或参考顺序，旧预览采用被拒绝；旧成果保留可查看。
