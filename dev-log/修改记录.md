### 17. 修复多分镜并发生图结果互相覆盖并补回历史结果
- **功能模块**：数据库事务 (`server/db.py`)、剧集生图 (`server/services/project_detail_service.py`)、分集工作台 (`z-admin/src/views/project/EpisodeWorkshopPane.vue`)
- **修改原因**：用户连续为多个 Beat 发起草图或渲染图任务时，每个请求在调用 GRS 前读取整份分集 `data_json`，任务完成后又用各自的旧快照整份覆盖。后完成的请求会抹掉先完成任务写入的 URL 和 job ID；前端同时只保存一个全局生成中 Beat ID，无法准确显示多个并行任务。
- **错误实例**：`job-c63e53ca3ffc`、`job-c12a3aa4e9e4`、`job-c1c7b670e106`、`job-8065266dd9c3` 均已完成，但最终只有最后写入的 Beat 2 渲染图保留在分集数据中。
- **修复方案**：
  1. 增加自动提交、异常回滚的短事务上下文；GRS 生成和七牛上传完成后才进入事务，使用 `SELECT ... FOR UPDATE` 锁定目标分集；
  2. 锁内重新读取最新 `data_json`，仅合并目标 beat 的草图或渲染字段，并在同一事务中将任务更新为 `completed`，杜绝不同 Beat 的并发丢失更新；
  3. 单 Beat 编辑接口复用相同的原子更新逻辑；前端普通设定保存改为仅提交文案与镜头字段，手动上传仅提交对应图片字段，避免旧图片快照反向覆盖新生成结果；
  4. 前端使用草图、渲染两个响应式 Beat ID 集合分别维护并发状态，按响应 `beat_id` 定向更新槽位，同一槽位去重且不同槽位可并行；
  5. 已从任务 payload 校验目标后，将上述 4 个任务的 URL、prompt、job ID 和状态幂等补回 Beat 5 草图及 Beat 2、3、6 渲染图。
- **测试与验证**：
  - 使用临时分集启动两个线程并发写入不同 Beat，图片结果和并发台词编辑均保留，测试记录已清理；
  - 后端 `py_compile` 通过，前端 `pnpm run build` 通过；
  - 数据库复查确认 Beat 2、3、5、6 均已关联指定任务和有效图片 URL。
